## 四、提炼的四大代码级根因与精确修复公式（供 `S12 / c102` 汇总入 `v34cand`）

1. **【RC1 - 最致命】`emptyAllIn -> nearCollapse` 逆洪流迎头 1:1 对撞漏洞（`v33-live.js:4730-4749 & 5184-5189`）**
   - **机制**：当对手 `q` 向我方发起满仓自杀梭哈（`inAtk > 0.15 * B && Bq < 0.08 * inAtk`）时，`offers()` 将其标为 `emptyAllIn = true` 并置 `nearCollapse = true`。随后 `buyLand` 第 `5184` 行 `if (o.nearCollapse)` 分支直接发送 `Math.max(0.12 * B, 0.30 * need)`（而 `need = elimCost + inAtk` 包含了来袭大军！），且**该分支漏掉了第 5177 行的 `if (inAtk > 0 && curAtk + pulse < ring1Cost + 2 * cntQ) continue` 护栏**！结果我方在敌方百万洪流刚发出的第 1 拍就迎头撞上去，把原本主场 `1:2` 的防守吸收优势变成 `1:1` 互换，白白多死 ~55 万兵。
   - **修复护栏**：
     ```js
     // 在 buyLand() 进入脉冲/出兵分支前：当敌方正在对我方倾泻满仓梭哈洪流 (inAtk > 0.12 * B 且对方家里已空 Bq < 0.05 * inAtk) 时，
     // 严禁主动出兵迎头 1:1 对撞！必须先在主场以 1:2 防守优势吸收洪流，等 inAtk 衰减到 <= 0.12 * B 再反推收割空壳！
     if (person && inAtk > 0.12 * B && g.bal[q] < 0.05 * inAtk) continue;
     ```
     同时在 `if (o.nearCollapse)` 分支中，脉冲上限应基于 `this.elimCost(g, q)` 而非包含 `inAtk` 的 `rawNeed`，并补齐 `if (inAtk > 0 && curAtk + pulse < ring1Cost + 2 * cntQ) continue;`。

2. **【RC2】`tryDeterrentCounter` 在我方主动进攻后误触发“反蚕食补刀”（`v33-live.js:2709-2827`）**
   - **机制**：我方在 `t=3640/3647` 主动向 `H#1` 倾泻了 139 万兵，`H#1` 在 `t=3703` 的 24.7 万兵属于自卫反击；但 `tryDeterrentCounter` 未检查 `this.hitTo.get(q)`，在 `t=3717` 又补了一记 25.4 万兵的“威慑反击”，直接把 `H#1` 逼成自杀梭哈。
   - **修复护栏**：
     ```js
     // 若我方在最近 120 拍内曾主动陆地攻打过 q，则 q 的回击属于交战反击而非无端蚕食，交由 buyLand 处理，禁止 tryDeterrentCounter 添油！
     if (!isFreshBeachhead && g.t - (this.hitTo.get(q) ?? -999) < 120) continue;
     ```

3. **【RC3】唯一健康缓冲盾（`isSoleHealthyBuffer`）在 `dMe >= 140` 时被双连锤砸穿（`v33-live.js:4940-4943, 5034, 5208-5215`）**
   - **机制**：被困在角落实盘唯一接壤真人 `q` 身后（且 `newNbs > 0`、`dq >= 100`）时，第 `5034` 行 `if (dMe >= 140) keep = Math.min(keep, 122 * L)` 强行覆盖了 `overHumanKeep`（`112 * L`），且第 `5214` 行非脉冲出兵分支没有任何 `hitTo` 冷却锁，导致线上 RTT 期间在 `t=3640` 和 `t=3647` 连发两记 `20.1%B` 重锤（共 139 万兵），自毁长城。
   - **修复护栏**：
     ```js
     // 1. buyLand 对同一真人目标强制 >= 16 拍冷却锁，杜绝 RTT 期间连发两记 20%B 重锤：
     if (person && g.t - (this.hitTo.get(q) ?? -999) < 16) continue;
     // 2. 当目标是高密度唯一缓冲盾 (isSoleHealthyBuffer && dq >= 100) 时，禁止 dMe >= 140 强行下调 keep：
     if (dMe >= 140 && !(isSoleHealthyBuffer && g.bal[q] / Math.max(1, g.terr[q]) >= 100)) keep = Math.min(keep, 122 * L);
     ```

4. **【RC4】线上模式 `updateShadowQuota` 因 WebSocket RTT 延迟误判 `isNoFullSend = true`（`v33-live.js:4025-4039 & 4080`）**
   - **机制**：`send()` 在 `g.online` 下设置 `pendingQuotaCheck = { t: g.t + 1, bal0, fee, want }`。由于线上指令有 2～7 拍 RTT，`g.t + 1` 时服务器尚未回包扣款；若在 `pc.t + 6` 窗口内恰好有一笔更小的指令落地或余额变动使得 `B < bal0 - fee` 且 `want >= 1.12 * actualSent`，就会在普通 FFA 局中误将 `this.isNoFullSend` 永久置为 `true`（本局在 `t=806` 即误触发）。
   - **修复护栏**：仅在 `want > 0.25 * bal0`（确实尝试了超 25% 配额的出兵）且检测到单拍精确扣款回包时才判定 `isNoFullSend`，或直接读取房间模式标志。
