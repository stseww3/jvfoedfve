# 流水线：怎么组织人手把图做出来

状态：**草案，等管理员点头后执行。** 美术方案（`ART-PLAN.md`）不变，这里只管“谁做、怎么流转、谁把关”。

背景：第一版做法是“各部分写细化稿，总装一个人审，审过才动手”。结果四个 agent 交稿后都在等一个人。管理员 11-13 的要求：细化工作多派 agent；要流水线；要有审美流水线；agent 数量不限；出图要用上显卡。

---

## 1. 原则

1. **活切小。** 一个工作包是一个人一口气能做完、能单独出图验收的东西：一族灯具、一种石材、穹顶外壳、一间房。
2. **谁做谁细化。** 线长只写清目标、约束和验收；尺寸、清单、做法由接包的人自己细化，写进工作包卡片。细化不再集中在一两个人身上。
3. **不设单人关口。** 每个工位至少两个人，或者有“没人回就按默认走”的规则。任何人不许空等：手上的包卡住了，就接下一个包。
4. **好看靠三样：标准、比选、评审。** 先把“好看”写成能打分的标准；关键的东西同时做几版并排挑；每批图都过评审团，不到线就退回。
5. **图说话。** 每次交付必须带图；评审只看图和清单，不看谁做的。
6. **重活都在管理员电脑上。** 云端那台 4 核机器只改代码、提交代码。

## 2. 工位

一个工作包依次经过：

| 序 | 工位 | 谁 | 做什么 | 出口 |
| --- | --- | --- | --- | --- |
| 1 | 立项 | 线长 | 写工作包卡片：目标、约束、验收、要拍的视角、要不要比选 | 卡片 |
| 2 | 细化和制作 | 制作 agent（比选的包 2 到 3 人各做一版） | 细化、写代码、离线出图自查 | 分支、提交、自查图 |
| 3 | 技术检查 | 检查 agent | 跑自动检查脚本，对照规则清单 | 过，或退回并写明原因 |
| 4 | 真机出图 | 出图 agent | 把这个包摆进测试世界里它自己的地块，用游戏截图（显卡） | 真机图 |
| 5 | 审美评审 | 评审团（每包至少 2 人） | 按标准打分，写具体改法；比选的包排名 | 过；退回；或前两名送总监 |
| 6 | 合并 | 总装 agent | 合进总装分支，重新生成总场景 | 总装提交 |
| 7 | 看板 | 出图 agent 加评审团 | 拍 12 个看板视角；评审团做整体回看，开反馈单 | 看板图、反馈单 |
| 8 | 管理员 | 总监转交 | 看板图加一句“谁改了什么”；关键比选项并排发给管理员挑 | 管理员的反馈，记成反馈单回到第 1 步 |

退回不算失败，是正常循环。一个包退回超过三次，线长介入：要么改卡片（目标定错了），要么换人或加一版比选。

## 4. 工作包卡片和交接

**卡片**：`plan/packages/<线>/<包名>.md`，线长建，制作 agent 往里补细化内容。固定栏目：目标（对应方案哪一节）；约束（坐标、尺寸、色阶、占用表角色、实体预算）；交付物（代码放哪、测试场景叫什么）；验收（评审看哪几个角度、技术清单）；要拍的视角；比选几版；依赖谁、被谁依赖。

**分支和文件夹**：每个制作 agent 一个自己的工作目录和分支（分支名里带 `c164-<包名>`），只改卡片里写的文件夹。公共文件只有总装 agent 改，要改的人在群里提。

**交接靠群消息，开头固定，方便扫**：

- `【交付】<包名> <分支> <提交> 图：<文件名>`（制作 → 技术检查）
- `【技检】<包名> 过` 或 `退：<原因>`
- `【真机】<包名> 图：<文件名>`
- `【评审】<包名> <各角度分数> 过` 或 `退：<最要紧的三条改法>`；比选包写排名
- `【合并】<包名> <总装提交>`
- `【问题】<问谁> <一句话>`

**图**都回传到云端同一个文件夹，文件名 `<包名>-<提交前七位>-<视角>.jpg`。里程碑的图另存进仓库。

**不许空等的规则**：问线长的问题 10 分钟工作量内没回，制作 agent 按自己写明的默认做法继续，并在卡片里记一笔。评审排到的人没空，由同角度的另一人或相邻角度的人补位。

**群**：每条线一个群（线长、本线制作、对口的评审和检查）；一个总控群（总监、八个线长、总装、工具、出图、标准、评审）。跨线的事只在总控群说。管理员只和总监说话。

## 5. 审美流水线

### 5.1 标准

`plan/aesthetics/RUBRIC.md`，由“审美标准”agent 写，总监批。把“顶级地图好在哪”拆成可以打 0 到 5 分的条目，每条写清 1 分、3 分、5 分各是什么样子，尽量配我们自己图里的正反例。只总结规律，不照搬任何别人地图的设计，别人的截图不进仓库。

评分分五个角度：

| 角度 | 看什么 | 主要用在 |
| --- | --- | --- |
| 轮廓和构图 | 缩成邮票大小还认不认得出“一横、一圆、一竖”；视线往哪走；有没有焦点；前中后景 | 看板视角、建筑、场地 |
| 明暗和光色 | 去色后天空最暗、墙是中间调、窗和灯最亮；亮区不超过三分之一；冷暖对比落在灰白石上；没有死黑 | 全部 |
| 质感和像素 | 近看 3 格内经不经得住；平铺有没有条纹；像素大小一致；边缘、接缝、细节密度 | 材质、模型 |
| 风格和逻辑 | 是不是电气时代；机器看不看得懂；管线有没有来去；一族东西像不像一套；有没有禁用的东西 | 模型、室内、整体 |
| 第一眼 | 不给任何背景，只看图五秒：看到了什么，哪里最抢眼，哪里看不懂，想不想走进去 | 看板视角、室内 |

**过线**：适用的每个角度不低于 4 分，没有红线问题。评审每次必须写出最弱的三处，即使给了过；改法要具体到“哪个视角、哪个部位、怎么改”。

**校准**：评审团上岗先各自给同一批图打分（旧样例场景的图和方案配图），对一遍差异。之后管理员每提一条评审团放过去的问题，标准里加一条对应的例子。管理员的眼睛是最终标准。

### 5.2 比选

第 3.1 节标了比选的包，同时由 2 到 3 个制作 agent 各做一版，互相不看。评审团不看作者，独立排名并写理由。前两名送总监；总监定一版，或者指定把第二名的某个优点并进第一名。对整体观感影响大的（入口样板段、石材、穹顶、天空和彗星、灯具母题），总监把前两名并排发给管理员挑。

落选的版本留在分支里，不删。

### 5.3 整体回看

每次合并后，出图 agent 拍 12 个看板视角，评审团五个角度各出一份整体意见：现在最弱的三处是什么，归哪条线。总监汇总成反馈单分给线长。看板图同时发给管理员。

## 6. 技术检查

工具 agent 写 `tools/check.py`，制作 agent 交付前自己先跑，检查 agent 复跑：

- 生成的贴图里有没有色板外的颜色（`palette.strays`）。
- 模型是不是 16 像素一格（`px` 等于 `scale`）；拉伸件的贴图沿拉伸方向是不是均匀。
- 用到的方块是不是都在占用表里；被重画的方块有没有被按原意使用。
- 展示实体数量：这个包多少，摆进去以后每个看板视角里多少，对照预算。
- 立面上有没有超过 5×5 的平墙。
- 文件有没有放在自己的文件夹里；有没有机密、第三方文件。

清单上脚本查不了的（门能不能走人、层高够不够、文字有没有超出“数字、符号、少量英文”）由检查 agent 看图看代码。

## 7. 出图：两条路都用

| | 离线渲染（CPU） | 真机出图（显卡） |
| --- | --- | --- |
| 用在 | 制作自查，材质的比选 | 审美评审、看板、给管理员的图 |
| 画面 | 和真机几乎一样，但不画粒子、方块实体、原版的云 | 最终效果 |
| 速度 | 准备约 10 秒，之后每张 1 到 5 秒（实测 22 张 54 秒） | 摆放约 2 秒，换资源包约 25 秒，每张几秒 |
| 并发 | 每个任务自带资源包，互不影响；排队执行 | 一个游戏一个世界，各包摆在自己的地块上 |
| 谁能跑 | 所有人，通过 `bin/job.py` | 只有出图 agent |

**离线队列**：现在同时只跑一个重任务、6 个线程、低优先级。管理员电脑空的时候可以放到两个。

**真机工位**（需要管理员同意游戏常开）：测试服和一个游戏客户端在流水线运转期间一直开着，窗口在后台，不抢键盘鼠标，占约 2 GB 显存和 2 到 4 个线程。测试世界按地块分给各个包（地块间隔 1000 格）。出图 agent 按“班车”跑：每隔几分钟把攒下的请求一起处理，合并各包的资源包、重载一次、挨个地块拍、回传。开之前照旧先查显存，空余不到 2 GB 不开；管理员要用显卡时说一声就关。

管理员电脑上的规矩不变：只在 `workspaces\c164` 里活动；不装系统级的软件；测试服只监听本机；不碰别的文件夹和别的任务。

## 8. 启动顺序和容量

1. **第 0 步**：把第一轮审稿结论（`reviews/R1-first-designs.md`）发给三位线长，他们按结论修订并切包。
2. **第一波，约 20 人**：总装、工具、出图、技术检查各 1；审美标准 1、评审 3；新线长 4（场地、大型机械、室内、动态）；已经说清楚的包先开工：材质 3 人、主楼 2 人、道具 3 人。
3. **第二波起**：各线长的卡片写好一批就加一批制作 agent；评审和检查按排队长度加人。
4. 每一波之后查云端机器的内存和负载。它只有 4 核，所有 agent 的命令都在上面跑，现在负载已经很高。可用内存低于 3 GB，或者命令开始超时，就停止加人，并报给管理员。

## 9. 总监（A0）做什么

- 批标准、批骨架和色板的改动、定比选。
- 每次合并后把看板图发给管理员，一句话说清谁改了什么；管理员的话记成反馈单分下去。
- 盯三件事：有没有人在空等；有没有包在同一个地方转圈；评审团的分数和管理员的反馈对不对得上。
- 不亲手写工具、不合并、不逐份审稿。
