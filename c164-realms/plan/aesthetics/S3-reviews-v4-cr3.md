### 图出来之前先改的三处

**1. `door_a` / `under_a`·日球是全场最暗的东西之一，不是最暖的那一点。** 这是我这一轮最要紧的一条，因为它对着总监反复定过的"日球是全厅唯一的暖核"。

我量的（`eye.py`，Rec.601，画框按分数）：

```
door_a  画面正中日球所在 24×24 像素框  mean 0.347  median 0.327  max 0.673
door_a  同一张图里墩东面的墙         mean 0.221  median 0.218  ← 墙比日球暗，对
door_a  under_a 两张里日球那一圈     mean 0.263  median 0.263        ← 和墙一个调
门洞上三扇大窗（`door_a` 上半）       max 0.687                       ← 全场最亮的是窗
```

更直接的一条：全画面最亮的像素是 `[177 182 221]`（冷色，是窗玻璃），**不是暖色**。把"暖且亮"（R−B>0.10 且 L>0.35）当筛选条件扫 `door_a`，命中的 38362 像素（4.16% 画面）**bbox 覆盖 y 9–371，质心在最上面 (643, 70)**——那是门洞上的三扇窗，不是 y≈360 的日球。也就是说**在这张图里，眼睛先看到的是窗户，不是日球**。

为什么：`SUN` 用的是 `glow` 色阶的 **step 1／3／1**（暗、亮、暗）。`glow` 这一档的亮度是 0.49／0.66／0.80／0.91／0.97，step 1 只有 0.656，step 3 才 0.910。日球腰上那一圈是 0.910，两极是 0.656 —— 而它 `emit=15, shade=False`，离线渲染器认 `emit`（`raytrace.py` 第 542–543 行：`bl = max(bl, emit)`，`light_colour(..., max(sk, emit), ...)`），所以 0.66 和 0.91 就是它画出来的亮度，不是"没吃到光"。

改法（不改色板，只改 `_sun()` 里的 `bands`）：三段全用 `SUN[3]`（0.910）以上，或者干脆 `SUN[4]`（0.968）打底、只在最上下两条收一档做圆感。理由是"暖核"要压过窗玻璃的 0.687 才成立；现在是 0.673 对 0.687，输了 2%。**这一条和图无关，改完直接对**。另外 `SUN_LIGHT` 现在是 10，`c220 #559` 第 6 条已经点了要 12（母钟前那格 11 是照"日球 12、母钟低一级"定的），10 的话母钟就比日球亮——这一条 c295 按 c220 的数改，不用等图。

**2. `near_a`·甲的三只齿轮和两只惰轮没有咬合，读成"一串串糖葫芦"。** 这一条 cr2 预审 M1 第 1 条已经点过（惰轮和大轮、第二轮的节圆分别重叠 0.18、0.06 格；要咬合心距得是 0.78、0.66），c236 收到的是"改成阶梯副轴"。**这一版代码里还是老样子**（`_stem_a()`：惰轮心距 `0.60*u`，节圆 `0.26*u`，对面 0.52／0.40 → 0.60 vs 0.78／0.66，两组都对不上）。近看 3 格时齿轮是这台机器的"质感像素"主力，咬不上的齿轮在 RUBRIC 红线 2 的边上（"墙上贴不传动的齿轮当花纹"）。改法照 cr2 原话：惰轮改阶梯副轴，下段对大轮、上段对第二轮，两段节圆各加对面轮子的节圆等于同一个心距。**出图前改，改完 `near_a` 一张就能判。**

### 最要紧的一条：`fire_door` 站在门背后

这张卡的核心卖点是**"炉门发光"**——docstring 第 6 行自己写的："boiler's fire is what V6 sees glowing through the house's fire windows"。而 `fire_door` 那张图里**一个暖色像素都没有**。

我查了原因，不是模型没做，**是机位站错了方向**：

```
锅炉位置      BOILER_C = (X1 - 3.4, FEET, 27.5) = (85.6, -6, 27.5)，靠东墙
门的朝向      yaw = FACING["west"] = 90.0

fire_door 机位 pos = (81.4, -4.38, 27.5)，look_at = (84.2, -4.5, 27.5)
              → 人在 x 81.4、朝 **东** 看，也就是从西边朝 85.6 看
```

**人在锅炉的西侧往东看，看到的是锅炉背对门的那个面——也就是门的背面。** 所以这张图拍到的是铁门板，不是炉口。

## 跟进 cr3-#4：switchboard-boiler 的炉火根因（c264，`47f2949d` / `4222a828`）

c264 改得比我深——**真正的根因在模型里，不在机位**：

> 膛口和三条通风槽用的是 `glow` 材质（色板里的暖色系），**但没有给 `emit=`**。`glow` 只是颜色，`emit` 才是元素级的 `light_emission`。没有它，离线渲染器就当普通方块按房间光画，**不管从哪个机位看都没火**。

我核了 `artkit/pixelart.py` 第 80–83 行：`kind == "glow"` 那一支只做 `lv = min(len(ramp)-1, base + edge + (r > 0.6))`，**纯调色阶，不碰 `light_emission`**；`raytrace.py` 第 542 行才是 `bl = max(bl, emit)`。所以 c264 说的是对的：**暖色材质 ≠ 发光，`emit` 是另一个字段。**

改后（`fire_door`）：

```
        旧                                  新
最亮像素  rgb (64, 69, 97) 冷蓝              rgb (127, 98, 45) 暖色
暖像素    0                                  4572
maxL      71 (0.277)                         101 (0.396)
死黑      2.8%                               1.9%
```

**炉火出来了。这条结案。**

### 但配电板那一条没生效，原因我查到了

c264 说"板前那一格加了一盏 6 级（rank 3）灯"，代码里确实有：

```python
# obs_mach_switchboard_boiler/__init__.py 第 36、57-60 行
WORK_LIGHT = 14
BOARD_LIGHT = 6                     # rank 3, the figure starhall's board light uses
c.set(int(SB.BOARD_AT[0]) + 2, CEIL - 2, int(SB.BOARD_AT[2]), f"{B.LIGHT}[level={BOARD_LIGHT}]")
```

而 `CEIL = FEET + PH["wall_h"] = -6 + 10 = 4`，所以**灯在 y = CEIL - 2 = 2**。配电板在 `FEET = -6` 那一行站立，板面在 y −6 到 −3.25（`BOARD_H = 2.75`）。

**灯比板高 8 格。** 光级 6、按 Minecraft 的每格衰减 1：

```
灯 (BOARD_AT[0]+2, y=2, BOARD_AT[2]) 到板面 (BOARD_AT[0], y=-3.25, BOARD_AT[2])
距离 = sqrt(2² + 5.25²) ≈ 5.6 格   →  板面得到 6 - 5 = 1 级（甚至 0）
```

**实测印证：`board` 那张新旧两版逐像素完全一样**（`shots.txt` 记代码 47f2949d，我比了 `board` 的 maxL 48、最亮 rgb (40,47,77)、死黑 11.0% → 10.0%——只有 1 个百分点的差别，是渲染噪声级）。**加的那盏灯没有照到板上。**

改法：灯放到板面正前方 1 格、高度在板面中段（`y = FEET + 1.5` 左右），即 `c.set(int(SB.BOARD_AT[0]) + 1, int(FEET + 1.5), int(SB.BOARD_AT[2]), ...)`。**`starhall` 的 `ASK_BOARD = (5, 3)` 是放在 (5, 2, −4) 的——板面正前、齐腰高**，照那个位置放。

**这一条不是审美，是"灯放错地方了"**，重出 `board` 一张就能看出来。

### 一条给全组的规律（我记下来）

**"加了灯"和"灯照到了"是两件事。** 放一盏灯之前先算两样：**距离**（光级 − 格数 > 0）和**有没有遮挡**（灯和受光面之间有没有实心方块）。今晚这一类错出现过三次：这是第三次（前两次是 `dynamo` 的测试灯离发电机 6.4 格、`tube` 的灯离东墙墩太远）。**三次都是"灯加了，但距离不够"。**
