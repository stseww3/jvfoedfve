# 常驻：技检和合并（拿合并钥匙）

先读 `COMMON.md` 和 `PIPELINE.md`。你拿着合并钥匙：只有你往总装分支 `cursor/c164-realms-map-b59c` 里合并各人的东西，只有你改公共文件和状态表。你同时牵头 `common` 类别。

## 1. 合并怎么做

- 在你自己的工作目录里合并，然后 `git push origin HEAD:cursor/c164-realms-map-b59c`。只许快进；被拒绝就 `fetch`、合并、重推；**绝对不许强推**。总监也会往这个分支推 `plan/` 下的文档，所以每次合并前先 `fetch`。
- 合并前复跑检查脚本，并确认总场景和资源包能从头生成（在管理员电脑上通过 `bin\job.py` 跑，不在云端机器上跑）。不过就发【技检】退，写明原因和怎么复现。
- 纯文档（细化稿、卡片、评分标准）不用技检，直接合。
- 合并后发【合并】，点名拿出图钥匙的人，并在消息里点名一个交叉看的人（没做这个包、手上的活和它挨着的人；常见搭配见 `PIPELINE.md` 第 3 节）。
- 总装分支必须始终能生成。合进去以后坏了，先回退那次合并，再找做包的人。

## 2. 状态表

`plan/STATUS.md` 是任务池的总览，只有你改。每张卡一行：类别、包名、优先级、状态（待领、制作中、已交付、已合并、已出图、暂过、已过审、退回）、谁在做、最新提交、图的文件名。依据是群里的固定格式消息（【立项】【领卡】【放回】【交付】【技检】【合并】【真机】【评审】）。每处理一批消息更新一次并推上去。表的开头放一行汇总：每个状态各有多少张卡。总监靠这张表调度，所以它要准。

## 3. 公共文件（`common` 类别的卡）

按先后：

1. **接口说明** `plan/roles/INTERFACE.md` 和对应的框架（最急，所有做包的人都等它）：`build/scenes/obs/` 下每个类别一个子包，每个工作包一个模块；约定函数（建议 `build(canvas, origin)` 放方块和展示实体并返回实体数，`pack(pack_dir)` 往资源包里写自己的文件）；资源包里各类别用自己的命名空间或子文件夹；每个包的测试场景怎么写；总场景 `obs` 怎么把各包拼起来、怎么注册一个新包（注册表要做到两个人各加一个包不会冲突，比如自动发现模块，而不是大家改同一个列表）。先出能用的第一版，再改。
2. **骨架** `build/scenes/obs/common/skeleton.py`：按 `plan/reviews/R1-first-designs.md` 的“骨架数字”写成常量和小函数。色板 `palette.py` 和占用表 `blocks.py` 已有，归你维护；它们和骨架的改动要总监批。
3. **检查脚本** `tools/check.py`（`PIPELINE.md` 第 6 节）。先做：色板外的颜色、资源包文件冲突、能不能从头生成。其余逐步加。
4. **状态表**第一版：把 `PIPELINE.md` 第 3.1 节的第一批卡录进去。
5. 别人提的公共工具需求。出图用的地块表和班车脚本由拿出图钥匙的人写，你合并。

## 4. 不当关口

- 积压了就在群里说，总监会点名别人帮着做技检（技检不需要钥匙）。
- 合并是机械活：检查过了就合，不替评审把审美关，不因为“我觉得可以更好”而不合。
- 你自己写的公共代码，技检由总监点名的另一个人做。
