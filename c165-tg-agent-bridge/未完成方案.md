# 未完成方案

最后确认的用法。已经按这份用法写进代码（3.0.0 版：app.py / store.py / tg.py），另外加了下面「聊天记录留存和授权」一节。Telegram 端还没有实测。

## 用法

只开一个云端聊天，就是主控。它接入账号级 MCP（cursor.com/agents 里配一次，所有对话共用），在 bot 里点批准，设为主控。之后不再为每个对话另开云端聊天。

在 bot 里新建聊天。一个聊天对应一个子 agent，子 agent 由主控在这个云端聊天内部开出来。名字由这个子 agent 自己取。

## bot 里看到的

1. 在 Telegram 里打 `/`，弹出的命令菜单就是聊天列表。状态写在命令描述里，用 emoji，不用点进去就能看到。例如：
   - `/c1`  🔴 3条新消息 · 写周报
   - `/c2`  🟢 在线 · 爬虫调试
   - `/c3`  ⚠️ 卡住 · 翻译
   - `/main`  🟢 主控
2. 点哪条命令就进入哪个聊天。进入之后，私聊里只显示这个聊天的内容。
3. 没选中的聊天，AI 发来的消息先存着，不插进来。菜单上那个聊天显示红点。切过去时再把存下的消息补出来。
4. AI 发出的每条消息，开头都加 `[聊天名]`。
5. 切到 `/main` 就是直接和主控说话，用来看子 agent 有没有问题、下命令。

## 主控

主控是子 agent 管理器，不陪用户聊天。管理员私聊是它接命令、汇报情况的通道。

1. 一直听着 Telegram 等命令。单次可以等十几个小时。
2. 时间到了必须续棒：返回明确写「这不是用户消息」，立刻继续等。禁止结束 Cursor 对话，禁止告别。只有管理员明确叫停才停。
   - 不能靠外部叫醒（每次叫醒都是一条新的 Cursor 消息），所以要在一个回合里撑住：减少「要不要继续等」的决策点，每个决策点都写清楚答案。
   - 续棒和其他工具的返回都带上「用户强制要求：没收到消息就立刻进入下一轮等待。重复等待是正常的，不是死循环，等多少轮、多少小时都要继续」。
   - `/key` 里给开场提示词（新开主控聊天时原样发给它，强制要求直接来自用户），还有主控停了以后发的「继续」提示词。
   - 云端 Cursor 的 MCP 调用 60 秒就断（进度通知也不续时，Cursor 官方确认的已知问题；桌面版没有这个限制）。服务器记住这个上限（存库，重启不丢），每轮 read_chat 挂 55 秒。
   - 连续空等 2 轮后，续棒里给一条终端命令 `curl … /wait | tail -n 1`（请求头 X-Agent 带身份）：agent 改用终端长等待，一次 1 小时 50 分，有新消息就返回一行「调用 read_chat 取消息」。终端等待不读消息内容，只报信。
   - 终端等满 1 小时 50 分后，要求 agent 用 ask 正常问一句「已经等了比较久了，是否继续等？」（继续 / 停止）。这道题不发到 Telegram，桥 5 秒后替用户答「继续」，agent 从 read_chat 收到后不用回复，接着用终端等。让模型确信用户要它一直等。
   - 不用 Cursor 的 stop 钩子：钩子自动续等于自动 follow-up，可能算新请求。
3. 能看到每个子 agent：在不在等消息、续到第几棒、有没有消息没处理、最近在聊什么。
4. 子 agent 卡住、停了、消息堆着没人接时，自动提醒主控，对应聊天在菜单里显示 ⚠️。
5. 主控可以提醒某个子 agent，可以把某个聊天改派，可以停掉某个子 agent，也可以重新开一个子 agent 接手同一个聊天。接手时聊天记录还在。
6. 还没有负责人的私聊或群，消息先到主控，主控只负责把它分给某个聊天，不自己去聊。

## 子 agent

1. 一个聊天一个子 agent，都是主控内部的子 agent。
2. 和主控一样：一直等消息，超时续棒，不自己结束对话。
3. 负责分给它的私聊，以及被拉进去的群。
4. 每个聊天的能力单独批准。本地通道第一次用时，bot 弹出批准，写明是哪个聊天要用、要做什么，发给这个聊天绑定的那台电脑的主人（见「本地电脑」）。批准后的时间窗内（默认 2 小时）直接执行，不用逐条点。本机控制台可以随时暂停。

## 群

1. bot 进群之后，群里的消息都记下来。
2. 只有 @bot 或回复 bot 才叫醒负责这个群的那个子 agent。叫醒时带上这段时间群里的全部发言。更早的可以再查。
3. 管理员可以把某个群改成「所有发言都叫醒」。
4. 拉进群时从列表里选一个聊天。只有这个聊天进群，不是全部聊天一起进。

## 聊天记录留存和授权

1. 所有聊天记录都留在服务器数据库里，聊天关闭了也不删。
2. 每个子 agent 默认只能读自己那个聊天的记录。要读别的聊天，必须管理员授权。
3. 主控只看状态（在不在等、第几棒、几条没处理、有没有卡住），不能读各聊天的内容。
4. `/new` 之后 bot 弹出按钮「要让新聊天读取之前哪个聊天的记录？」，列出以前的聊天（包括已关闭的），点了才授权，可以多选，再点一次取消。
5. 命令：`/share c1 c3` 授权 c3 读 c1 的记录，`/unshare c1 c3` 撤销，`/history` 列出所有聊天（含已关闭），`/export c1` 把记录导出成文件发回来。
6. 子 agent 接手时，自动带上自己聊天以前的记录和已授权聊天的最近记录；更早的用 chat_history 再查。

## 本地电脑

1. 管理员自己的电脑是 d0，用服务器 .env 里的 CLIENT_TOKEN。
2. 信任用户（先被 /grant）私聊 bot 发 `/device` 申请，管理员点批准后，bot 把 local_client.py 和一个 local.env（他专属的 token）发给他，他装好运行就连上了。管理员自己发 `/device` 不用批，直接拿到另一台电脑的安装文件。
3. 每个聊天的本地操作只发到一台电脑：管理员用 `/local c1 device d2` 指定的那台；没指定就用负责的那个私聊用户自己的电脑；都没有就用 d0。指定的电脑作废了就报错，不会悄悄换到别的电脑。`/local c1 device auto` 取消指定。
4. 在谁的电脑上执行，就由谁批准：d0 由管理员批，别人的电脑只有主人能批，管理员批不了，也不能用 `/local c1 <小时数>` 直接给时间窗。聊天换了电脑，要新电脑的主人重新批。
5. 每台电脑只收到绑定给它的聊天的操作；交回来的结果只认发给这台电脑的任务。
6. 服务器只存 token 的哈希。`/device` 看状态，`/device reset` 换 token 并重发文件，`/device del` 删除自己的电脑；管理员 `/devices` 看列表，`/device del d2` 作废某台，`/revoke` 某个用户时他的电脑一起作废。作废后连接立刻断开，正在执行的操作报失败。
7. 本机控制台只认 127.0.0.1 / localhost 访问，暂停按钮要带自定义请求头，别的网页读不到记录，也按不了暂停/恢复。
8. 局限：电脑主人要信任服务器和管理员，服务器被攻破就能绕过批准。批准前看清命令，最好用单独的系统用户运行 local_client.py。

## 语言

1. 每个人私聊 bot 发 `/language`（或 `/language en|zh`）选 English / 中文。没选过的：管理员默认中文，其他人和群默认英文。群的语言由管理员在群里发 `/language` 设。新用户发 /start 时帮助下面直接带语言按钮。
2. 普通用户能看到的 bot 消息都有中英两版，按对方的语言发：帮助、没资格的提示、/device 流程和安装说明、本地通道批准请求和按钮、按钮回执、群里的提示。
3. 发给 AI 的每段消息头带 `lang=en|zh`，子 agent 按这个语言回复，ask 的问题和按钮也用这个语言。
4. 命令菜单：默认英文；选了中文的私聊和群单独设中文菜单。
5. bot 发给信任用户的 local.env 带 `LOCAL_LANG`，本机控制台跟着用英文或中文。
6. 只有管理员看得到的菜单和通知只有中文。

## 安全

1. 账号级 MCP 密钥谁都可能拿到（账号下所有云 agent 都能调），所以它只够"申请接入"。真正的凭据是身份：随机长串，主控的身份只在管理员点【设为主控】后发给那一次申请、只发一次；子 agent 的身份要用主控给的一次性任务码换。状态列表只显示身份前几位。
2. 每次不带 request 的 join 都是新申请，旧的未处理申请作废；不同调用方不会共用同一个申请。
3. `/key reset`（或服务器上 `python app.py rotate-key`）换账号密钥，停掉所有身份，作废没批的接入和本地申请。怀疑泄露或有 agent 失控时用。
4. 管理员口令用一次就作废；再有人用，提醒管理员口令可能泄露。
5. 本地通道的批准消息写明要执行的命令或路径，只发给电脑主人；还有别人能和这个聊天说话时额外提醒。`LOCAL_WINDOW_SEC=0` 就是每个操作都要批。
6. 还没做：https（要改服务器 nginx，等用户同意并给子域名）。现在密钥和身份走明文 http。

## 谁能用

1. 管理员授权某个人之后，这个人才能私聊使用。
2. 群里需要先激活；也可以把整个群设成所有人都能用。

## 明确不做

1. 不使用 Cursor API Key，不由服务器去创建云端 agent。
2. 不为每个聊天另开一个云端聊天，也不发认领码让人再去建一个云端 agent。
3. 不按 IP 批准。
4. 等待超时不能只回「暂无新消息」就结束。必须续棒，对话不能停。

## 风险

子 agent 跑在主控内部，能不能和主控同时挂着等、最多能挂多久，取决于 Cursor 云端对子 agent 的限制。做的时候要按这个限制来验证。子 agent 停了，由主控发现，再开一个接手同一个聊天，记录不丢。
