本轮新发现，会影响后面的逐局复盘：

## 1. 节拍与指令通道

### 1.1 一拍里的结算顺序

`n8 @36934`。先问钩子 `__fx.strategyBot.beforeTick()`，返回 `false` 就跳过这一拍。然后依次：内置 AI 出手 → 配额上限增长 → 经济（利息、地租）→ 陆攻推进 → 船 → 存活检查 → 统计与“占满全图”判定 → 和平投票 → 队伍合计（每 32 拍重算）→ 录像记一步 → 拍号加一并调用 `afterTick` 钩子。

### 1.2 联机时指令每 7 拍执行一批

`af2 @670729`（联机驱动），常量 `af4 = 7`。服务器把所有人的指令打包下发，客户端只在拍号是 7 的倍数时取出一包，在当拍结算 **之前** 逐条执行。

录像实证：13 局、出生阶段之后共 34129 条指令，执行拍号对 7 取余全部是 0（`out/cmd-batch-check.txt`）。

由此得到三条对策略有用的事实：

- 从策略发出到真正执行，9 局的中位数在 11~14 拍，最短 2~8 拍（按捐款对账，`out/donation-ledger.txt`）。客户端卡顿时更久：A099 中位 20 拍、最长 104 拍，A029 最长 141 拍。
- 发出时看到的余额和局面，到执行时已经变了。引擎按 **执行时** 的余额重新算金额和手续费。
- 一批里同一个人可以有多条同类指令。13 局里每局都出现过，最多 9 条挤在同一拍。所以“每拍只能发一条”不是引擎的限制。

### 1.3 指令表

解码 `ql.ee @50269`，编码 `ql.rV @51086`，处理函数都在 `qj`（全局路径 `bB.qi`）。

### 1.4 校验不过就静默丢弃

每个处理函数开头是一串 `if (!条件) return;`。不通过时不扣钱、不报错、不给发起人任何回执。

录像只记通过校验的指令：捐款和发船是在 **全部** 校验（含配额）之后才调用记录器 `bC.rg.rh`。陆攻是在金额、目标、进攻槽校验之后记录，最后还有一步 `ap.jf.jt` 可能失败，所以录像里的陆攻有极少数没有真正打出去。

### 1.5 各种指令的手续费

手续费都按 **全部余额** 的固定比例收，和比例参数无关（`a5M.n2 @145958`、`a5M.rD @146160`）。

| 指令 | 手续费 | 出兵量 |
|---|---|---|
| 陆攻 | `g0(12B,1024)` = 1.17% | `min(g0(B×(pct+1),1024), B−手续费)` |
| 发船、追船 | `g0(32B,1024)` = 3.125% | 同上；不足 60 兵补到 60 |
| 捐款 | `g0(64B,1024)` = 6.25% | 同上，再受收款方空间限制 |
| 越山进攻 | `max(g0(B,10), 1000)` | — |
| 召回、撤回进攻 | 0 | 撤回的兵退回余额，超过上限的部分丢失 |

## 2. 组队

### 2.1 敌我判定

`dh.fS @669310`：两人队号相同且不为 0 才是队友。队号 0 的玩家互相也是敌人。

### 2.2 分队算法

`dP.ee @662686`，联机团队局在开局时跑一次。名义队数 = 房间模式 + 2。

1. **每个真人的颜色偏好**（`aej @663777`）。把自己选的颜色和 8 种队色（红、绿、蓝、黄、品红、青、白、黑）比 RGB 距离，最近的是第一志愿，次近的是第二志愿。第一志愿给该队色 4 票，第二志愿 1 票。
2. **队色排名**（`aKa @664325`）。按票数从高到低排，第 k 队用排第 k 的颜色。
3. **战队标签**（`aek @664560`）。名字里第一个 `[` 到 `]` 之间 1~7 个字符，转大写去空格，就是标签。只有一个人带的标签也算一个“战队”。
   - 如果最大的战队人数 > `g0(真人数, 队数)`，队数减一，重复直到不超过或只剩 2 队。
   - 战队从大到小，**整块** 放进它成员最偏好的那个队色对应的队。只跳过两种队：颜色不在当前队数范围内的，和人数已经严格多于其他所有队的。整块放入时不看每队人数上限。
4. **散人**（`ael @665625`）。每队上限 = `ceil(真人数/队数)`。没标签的人先按第一志愿进队，满了按第二志愿，还进不去的从最后一队往前填空。
5. **内置 AI**（`aem @666183`）。队数 < 8 时，内置 AI 全部留在 0 队，也就是和所有人、和彼此都是敌人，同时队数加一。队数 = 8 时内置 AI 按 `1 + 编号 % 8` 轮流进队。

### 2.3 带同一个标签的 10 个号

沙箱（`out/live-rules-check.txt` T1，每格 400 次）：10 个同标签的号 100% 落在同一队。代价是队数被压缩，例如名义 8 队、真人 25 → 实际 2 队；真人 40 → 4 队；真人 60 → 6 队。

录像实证（`out/replay-summary.txt`）：用规格书预测的队号和结算记录比，名字能在录像里对上的 107 行全部一致。队数也对得上，例如 A029 名义 8 队、真人 36，预测 3 队每队 12 人，我方 10 个号全在 1 队。

### 2.4 不带标签的 20 个号

| 情形 | 名义 3 队 | 名义 5 队 | 名义 8 队 |
|---|---|---|---|
| 颜色各自随机 | 100% 分散到 3 个队，最大一组约 8.3 人 | 约 99% 分散到 5 个队，最大一组约 5.6~6.1 人 | 70~80% 分散到 8 个队，最大一组约 4.1~4.6 人 |
| 全部选同一种颜色 | 真人 80 时 61% 全在一队；真人 40 时 96% 分成 2 队 | 多数分成 3~5 队 | 真人 60 时多数分成 4~6 队，最大一组约 6.6 人 |
| 同一标签 | 100% 同队，队数压到 2~3 | 100% 同队，队数 2~4 | 100% 同队，队数 2~4 |

B034 是实例：9 个无标签的号被分到 1、2、3、4 四个队（1+2+4+2），规格书对 9 个号的预测全部命中。

### 2.5 对策略的含义

- 同标签保证同队，这条是确定的。
- 同标签的人越多，实际队数越少、每队越大。10 个号进 20 人房间时，对面那一队也是 10 个真人。
- 不带标签时，选同色只能提高同队概率，受每队人数上限约束，做不到全员同队。

### 2.6 数据提醒：三局的“队伍”数据混了不同对局

- **A015**：录像里只有 4 个 `[APEX]` 名字（16~19 号位）。另外 6 个号的结算行号位是 0~5，录像里这些号位是别人。两组的队伍土地合计在相近时刻对不上（talon5 行 t=5005 时 2 队 53667 格，ryan_m 行 t=5180 时 2 队 197164 格）。结论：6 个号和 4 个号在两场同时进行的对局里。
- **A086**：录像里 9 个 `[APEX]`，没有 sora_w。sora_w 的结算行有 1、2、3 三个队的土地，其余号只有两个队。结论：sora_w 在另一场对局，卡片里的“分队 {2:9, 3:1}”不是局内分队。
- **A073**：录像头是 2 个真人、非团队局，是 alex_k 对 kaito9 的 1v1。

## 3. 捐款与 6.25% 税

### 3.1 执行条件

`qj.qv @52024`，依次检查，任何一条不满足就静默丢弃：

1. 对局进行中；发起人活着且没离场（`a5M.hl @144759`）。
2. 是团队局；对象不是自己；对象活着且是队友（`a5M.rn @147572`）。
3. 金额至少 1（`a5M.rD @146160`，见下）。
4. 配额够（`ca.ei @373526`，见第 4 节）。

### 3.2 金额与税

设发起人余额 B，比例参数 pct（0~1023），收款人余额 Bq、领土 Lq。

```
税   = g0(64 × B, 1024)                       # 6.25% × B，与 pct 无关
想捐 = g0(B × (pct + 1), 1024)
到账 = min(想捐, B − 税, 150 × Lq − Bq, 15e8 − Bq)   # 小于 1 则整笔作废
发起人余额减少 = 到账 + 税
```

出处：`a5M.jB @146531`（想捐）、`a5M.rD @146160`（税）、`a5M.a6a @145816`（收款方空间）、`cd.qt @348892`（记账）。

注意两点。第一，税按执行时的余额算，不按到账量算；收款方快满时，到账被压得很小，税照收全额。第二，B 是执行那一拍的余额，不是策略发出时看到的余额。

### 3.3 不同比例下税有多重

`out/live-donation-check.txt` 表 B1（收款方空间充足时）：

| pct | 到账占 B | 税占 B | 税 ÷ 到账 | 发起人共减少 |
|---|---|---|---|---|
| 51 | 5.08% | 6.25% | 1.231 | 11.33% |
| 102 | 10.06% | 6.25% | 0.621 | 16.31% |
| 255 | 25.00% | 6.25% | 0.250 | 31.25% |
| 511 | 50.00% | 6.25% | 0.125 | 56.25% |
| 959 及以上 | 93.75% | 6.25% | 0.067 | 100% |

策略日志里出现过的比例换算（`out/quota-table.txt` 表 1）：pct=129（旧版下限附近）到账 12.7%，税是到账的 0.49 倍；pct=155 是 0.41 倍；pct=180 是 0.35 倍；pct=320 是 0.20 倍；pct=380 是 0.17 倍。

同样的总量分两次捐，要交两次税。单看税，一次捐大额最省；但大额更容易撞配额（第 4 节）。

### 3.4 内置 AI 的捐款不走配额

`qm.kx @49660`：内置 AI（含离场真人）给队友捐款时，同样交 6.25% 税、同样受收款方空间限制，但 **不检查配额**。

## 4. 反喂养配额

### 4.1 规则

`ca @372839`（全局 `ao`）。

- 每个玩家有一个“作为收款人已用的点数”，开局 0，只增不减。
- 全场共用一个上限，开局 15。每逢拍号 % 100 == 99 增长：t < 1071 加 4，t < 2142 加 6，t < 3213 加 8，之后加 10（`ca.ee @373656`）。
- 一笔到账量为 v 的捐款消耗的点数（`aOc @373222`），其中 `uv = 1 + g0(地图陆地格数, 300)`：

| 时段 | 点数 |
|---|---|
| t < 357 | `2 + g0(100v, uv)` |
| 357 ≤ t < 714 | `2 + g0(100v, 4uv)` |
| 714 ≤ t < 1071 | `2 + g0(100v, 10uv)` |
| 1071 ≤ t < 2142 | `2 + g0(100v, 30uv)` |
| 2142 ≤ t < 3213 | `2 + g0(100v, 100uv)` |
| t ≥ 3213 | `4 + g0(100v, min(100 × 收款人领土, 1e9))` |

- 判定（`ca.ei @373526`）：已用 + 本笔点数 > 上限 → 拒绝，已用不变。否则已用加上本笔点数，放行。
- 不检查的情形（`aOb @373800`）：单机；t ≥ 4284；收款人是内置 AI 或已离场的真人。

### 4.2 换算成“一笔最多能收多少兵”

以陆地 664497 格的地图为例（uv = 2215），收款人此前没收过款（`out/quota-table.txt` 表 2，含其余 5 张地图）：

| 时刻 | 上限 | 单笔最多到账约 |
|---|---|---|
| t = 1070 | 55 | 1.2 万 |
| t = 2141 | 121 | 8.0 万 |
| t = 2200 | 129 | 28 万 |
| t = 3200 | 209 | 46 万 |
| t = 3213 | 209 | 约（上限 − 4）× 收款人领土：领土 2000 格时 41 万，领土 2 万格时 412 万 |
| t ≥ 4284 | 不限 | 只受 150 × 领土的余额上限限制 |

## 5. `window.ao.iD(对象)` 读的是界面滑杆

`ca.iD @372933`：

## 6. 被拒的捐款在策略那边发生了什么

### 6.1 引擎一侧（确定）

- 本机发起函数 `qg.qt @48792` 联机时只做一件事：调用 `aWM.qw @588542` 把指令发给服务器。两个函数都没有 `return` 语句。
- 指令在下一个 7 拍批次才执行，校验不过就丢弃，不扣钱、不回执（第 1.4 节）。

### 6.2 “恒返回 true”来自适配层（推断，证据充分）

策略写的是 `if (g.donate(pct, bestTarget, me)) { …写日志… }`（L4508 起）。日志行只在返回真值时才写。12 局里有 1413 次写了日志但录像里没有对应指令，所以适配层的 `g.donate` 在引擎最终拒单的情况下也返回了真值。适配层源码不在仓库里，原因只能推断：发包那一刻它无从知道 7 拍后的结果。

### 6.3 策略一侧的后果（按镜像源码，对应最新一版）

`tryDonateToTeammate` 末尾（L4508–4517）在 `g.donate` 返回真值后做三件事：`lastDonateTick = g.t`、`cmds++`、写 `[HL-DISPATCH]`。

`Policy.act` 的相关顺序（L4939–4963）：

```
cmdsBefore = this.cmds
扩无主地 → buyLand（买地 / 进攻）→ 拓宽战线的船
if (this.cmds === cmdsBefore) tryDonateToTeammate   // 前面没出手才捐
if (this.cmds === cmdsBefore) idleBoats              // 前面没出手才派闲船
跳岛
```

所以一次被拒的发起会造成：

1. 捐款冷却重新计 24 拍。实测同一个号每 25 拍发起一次。
2. 当拍不再派闲船，因为 `cmds` 已经加一。
3. 兵没有送出去，也没有扣税，留在家里。

它 **不会** 让 `buyLand` 少跑，因为捐款排在买地之后，并且只有前面没出手时才会尝试。和捐款有关、会提前退出 `act(g)` 的只有 `tryEmergencyBossRescue(g) && g.online` 这一处（L4928，核心期之前是 L4847），需要队里有 Boss。这个急救分支的最低比例是 55/1024：到账 5.5% 余额，税 6.25% 余额，税比到账还多（L4277）。

以上顺序只对有完整源码的最新一版成立。较早的两版（日志指纹不同）一版源码被截断在这段之前，一版没有源码，顺序未知。

### 6.4 实测到的形态

A029 的 kaito9：全场发起 94 次，被执行 9 次，多数时候每 25 拍一次。它一直是“被围住”状态；t=2075 到 t=3600 之间余额从 51.6 万涨到 131.5 万，密度从 59 涨到 150（余额硬上限），到上限后利息归零（`out/ledger/A029.donations.tsv`）。这就是广播里说的“内陆高密度停滞”，在这个号身上直接成因是配额拒单，不是引擎卡住。

## 7. 经济与上限（复盘会用到的部分）

- 利息每 10 拍结一次：`余额 += max(g0(利率 × 余额, 10000), 1)`。利率随领土占比查表（约 1%~2.6% 每 10 拍），t < 1920 时有一个随时间下降的保底。
- 软上限 = 100 × 领土：超过后利率按超出比例递减。硬上限 = 150 × 领土：到了就没有利息，收款也收不进。
- 地租每 100 拍加一次，等于领土格数。
- 离场真人利息为 0（`cd.aMi`）。

## 8. 船

出处集中在 `aaJ @631508`（逐拍移动与交战）、`aaM @629469`（到达与登陆）、`qj.iB @52316`（发船）。沙箱比对：移动 / 损耗 / 交战 4946 拍、靠岸 4000 例，0 不一致。

### 8.1 发船

- 条件：地图允许走水；自己有海岸；全场 ≤ 512 条、每人 ≤ 8 条。
- 手续费 3.125% 余额。装载量按比例算，不足 60 补到 60。

### 8.2 航行

- 速度（像素 / 拍）= `(250000 + min(20×兵, 300000) + min(兵>>3, 50000)) / 65535 / 16`。60 兵 0.240，1.5 万兵 0.526，10 万兵 0.536，40 万兵 0.572。
- 损耗：每 5 拍掉 `max(1, 兵>>7)`。1.5 万兵以上的船每走 100 像素掉 24~27%；1000 兵的船掉 43%；60 兵的船走不完 100 像素。

### 8.3 船对船

- 每逢奇数拍结算。两条船距离 < 7.5 像素、主人不同且不是同一非零队，就互相伤害。
- 兵少的一方损失 `max(1, g0(自己 + g0(对方−自己,10), 10))`，兵多的一方损失 `max(1, g0(对方,10))`。例：1 万对 1 万，每次各掉 1000；1 万对 1000，小船掉 190，大船掉 100。
- 挨打的船减速到约 0.038 像素 / 拍，几拍后恢复。兵掉到 0 的船移除。

### 8.4 登陆

`aaM.acN @631178`，按登陆格的主人分四种：

| 登陆格 | 结果 |
|---|---|
| 自己的地 | 兵回到余额，超过上限的部分丢失 |
| 队友的地 | 走移交（8.5） |
| 无主地或敌人的地 | 用全部兵发起或并入一次陆攻，不再收手续费 |
| 同上，但对这个目标没有进行中的进攻、也没有空闲进攻槽 | **整船兵丢失** |

进攻槽：真人数 < 16 的局每人 12 个，否则 8 个；内置 AI 4 个。

### 8.5 船靠到队友地上

`qm.rE @49792`：

```js
rE: function (player, qu, iI) {            // 船主，地主（队友），船上兵数
  if (!bD.gv.rF(iI, qu)) { …; return; }    // 队友余额已到上限 → 兵丢失
  if (!ao.ei(qu, bR.g6[0])) return;         // 队友配额不够 → 兵丢失
  bD.gv.gy(qu, bR.g6[0]);                   // 否则兵加到队友余额
}
```

- 不收 6.25% 税（发船时已经付过 3.125%）。
- 占用队友的配额，点数公式和捐款相同。
- 被拒时没有任何补偿，船已经没了。沙箱 4000 例靠岸里，这条路径出现 352 次配额丢兵、52 次到顶丢兵，与规格一致。

对策略的含义：开局前 2000 拍配额最紧，这时把船开到队友的海岸，既可能白丢一船兵，又会把队友的配额提前占掉，后面真正的救援捐款就过不去了。第 4.5 节 A047 的 riku_x 是实例。

### 8.6 追船与召回

- 追船（指令 4）：手续费 3.125%，目标必须是敌船。追到 7.5 像素内开打。
- 召回（指令 4，比例 849）：免费，船沿原路返回，优先靠自己的地。已在返航的船不能再改。

## 10. 存活、崩溃、出局

`cZ.aOV @372566`，每拍对每个活着的玩家检查。每人有一个“峰值领土”：

```
若 领土 ≤ g0(峰值, 4)      → 出局
否则若 领土 ≥ 峰值          → 峰值 = 领土
否则                        → 峰值 −= max(1, g0(峰值 − 领土, 1000))
```

- 出局（`cY.dt @333688`）：土地全部变成 **无主地**，余额清零，船移除。正在打它的进攻自动改成打无主地。

- 含义：一个号从 2 万格被打到 5000 格就直接出局，剩下的 5000 格谁也拿不到现成的，要重新当无主地去占。不存在“打到最后一格”的过程。

### 11.3 投票类型与门槛

类型（`ce.aBM @645029`）：存活 ≥ 3 人、第一名土地 < 50%、领先队余额 < 全场余额的 50% → “平局”型；否则“胜负”型。

票按投票人的领土加权，每人一票。分母 ea = 在场真人（活着且没离场）的领土合计。

| 类型 | 赞成票门槛 |
|---|---|
| 平局 | `max(g0(3×ea, 4), 1)`，即 75% |
| 胜负（团队局） | 百分比 = `clamp(1600 − 12 × 领先队土地%, 400, 1000) / 10`，再乘 ea |

### 11.4 计票

`cu.aBI @191906`，投票持续 360 拍，每拍检查：

- 赞成 ≥ 门槛 → 通过，对局结束。
- 反对票 ≥ `max(ea − 赞成门槛, 1)`（赞成已不可能达标）→ 4 拍后失败。
- 还剩 180 拍时，赞成 × 3 < 门槛 → 提前失败。
- 到时间 → 失败。
