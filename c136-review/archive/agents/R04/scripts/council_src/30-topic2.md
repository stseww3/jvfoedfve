## 2 议题二：超级版本必须改的八处，和每一处会在哪里反咬

写法：每一项先给证据，再给代码位置和方向（公式里的希腊字母是待定参数，取值由 §1.7 的 G1~G3 定，我不给数），然后是**在我复盘过的哪一局哪一拍会出反效果**、要加的护栏、G1 的正反例。行号是 Vc（`v27-team-c116.js` / `spawn-coordinator-c116.mjs`）的。

排序的依据不是「哪项损失最大」，而是依赖关系：第 1 项不修，后面每一项量出来的效果都混着重复单和晚到；第 2、3 项决定 1500 拍前拿到多少地；第 4~7 项是 1500 拍以后的兵往哪里去；第 8 项是两处独立的小锁。

### 2.1 通道层：一拍一条的仲裁、本机在途账本、按需要量封顶的连发

**证据。**
- 同一个决策拍出两条指令的 399 个号·拍，第 2 条落地 0 次，确定没落地 173 次；其中 1500 拍以后的 109 次，想出的兵合计 516.6 万。A081 的 17 个号·拍里 15 个是「无主地 + 内置 AI」：先发的是无主地扩张，被挤掉的是买地。
- 重复单 2,763 条 33,708.6 万兵，占打人 / AI 出征兵的 52%；去掉 A073 是 2,439 条 14,414.6 万兵（51%）。
- 同号同拍 ≥3 条的清仓批：600~1499 拍 302 批 1,801 条，1500~2999 拍 194 批 1,502 条。
- 600~1499 拍 1,113 条陆攻落地时目标已经出局（想出 267.4 万兵）。全量上我方 600~1499 拍 42% 的陆攻落在无主地上，别的真人 16%。

**代码位置。**
- `Policy.act`：`L4838` 每 `P.period` 拍一个决策拍；`L4941` `expandNeutral` 和 `L4942` `buyLand` 之间没有「本拍已发过」的守卫，而 `L4962`、`L4963` 的调度和闲置发船是有的（`this.cmds === cmdsBefore`）。
- `Strategy.send` `L479~487`：`g.attack` 返回真就 `cmds++`，不记这条指令是什么、发给谁、多少兵。
- `Policy.buyLand`：`L5459` `curAtk = g.attackTroopsOn(me, q)` 读的是引擎里已经生效的在途兵；`L5575`、`L5589`、`L5596` 三道「在途够了就不加」的闸门都用它；`L5353` 的 `over` 和 `L5446` 的 `avail` 用的是当前余额；`L5449~5454` 买内置 AI 的分支没有任何在途检查。
- c110 的 `Strategy.send` `L529~533` 有一个在线才生效的「同一目标 15 拍内不重发」，它的重复单占比是 14%（B034）；但它在调 `g.attack` 之前就记了时间（`L532`），桥不受理的时候这 15 拍也白等。

**方向。**

1. *仲裁*：一个决策拍里所有想发的指令先收成候选，按价值排，只发第一条，其余留到下一个决策拍重新评估。不要按代码顺序先到先得。
2. *在途账本*：每条被受理的指令记一行 `{目标 q, 种类, 比例 f, 估计兵力 x = f×B(τ), 发令拍 τ}`。闸门改读
   `curAtk'(q) = attackTroopsOn(me, q) + Σ 未销账的 x(q)`，
   `B' = B − Σ 未销账的 (x + 手续费)`。
   `L5353`、`L5446`、`L5459` 和 `L5450` 的需要量都换成带撇的。
3. *销账*：看到 `attackTroopsOn(me, q)` 增加了约 `x`（指令落地）→ 销；`q` 出局或不再接壤 → 销（引擎会改道或作废）；超过 `W` 拍没有动静 → 销并记一次「丢单」。`W` 不取常数，取这个号最近若干条指令实测的「发令到落地」延迟的高分位乘一个系数 `κ_W`。
4. *通道健康度*：上面那个实测延迟本身就是策略能拿到的唯一通道信号。延迟高分位超过阈值 `D*` 时进入保守模式：每个目标同时只允许一条未销账指令，全局未销账的出兵比例不超过 `F_stall`。
5. *连发封顶*：新指令要发之前检查累计比例
   `1 − Π_j (1 − f_j − 12/1024) ≤ F(q)`，`j` 取所有未销账的陆攻加上这一条。
   `F(q)` **不是常数**：对「需要量算得出来、打完能拿下」的目标取 `min(F_max, (1.25×need + 3×cnt + fee) / B)`，对健康真人的脉冲取单发的 `pulseFrac`。

**护栏。**
- 账本和 `pulseFrac` / `F(q)` **必须成对验收**：只上账本不重定脉冲，出手会变轻。
- 销账只用「目标身上我的在途兵变了」和「目标没了」两种硬信号，不用余额差。
- 账本条目带上限：单个目标的未销账条目超过 `N_max` 就强制清掉最老的，防止账本本身卡死出手。
- 保守模式只限制「非紧急」指令；被打时的还击和救急调度不受限。

**G1 的正反例。** 正例（必须只发一条 / 必须等回执）：A083 `ryan_m` 905~955 拍；A081 的 17 个同拍双指令。反例（不许拦）：上表第一行的四次。

### 2.2 留兵底线的参照物不许是队友；小额的买地不该被整笔底线卡住

**证据。**

- 600~1499 拍贴着内置 AI 的 16,640 个号·决策拍里，出手的 4,805 个（29%），被闸门卡住的 10,463 个（63%）。别的真人这一段 72% 的陆攻都在打内置 AI。

**代码位置。**
- `Strategy.threatOf` `L417~444`：`L436` 只跳过目标自己和我自己，队友不跳；`L439` 取的是 `bal[o] + attackTroopsOn(o, q)`。

**方向。**
1. `threatOf` 里遇到 `isTeammate(g, o)`（`L3927~3929`，按队伍判，不按名字）就跳过。
2. 参照物是敌方真人时，底线表达的应该是「买完以后我多暴露给谁」，而不是「我现在够不够格」。买这块地要花 `x = 1.25×need + 3×cnt`；当 `x + fee ≤ ε×B` 时放行：不买，我对那个敌人的暴露一点没少，只是少了地。
3. 其余情况保留底线，但参照物换成**和我接壤、或买完以后会和我接壤的敌方真人**，按 §2.5 的「够得着我多少」算，不取对方的整个余额。

### 2.4 调度按反喂养配额算账

**证据。**
- 调度发出 → 落地：2142 拍前 259 → 6（2%），2142~3212 拍 697 → 73（10%），3213~4283 拍 678 → 189（28%），4284 拍以后 453 → 415（92%）。全量日志里 23,093 行调度 / 捐款有 14,751 行（64%）被标成疑似被拒（`likelyRejected`）；squad10 赢的局 42%、输的局 76%。
- 没落地的原因（用真引擎的配额账重判）：2142 拍前 237 笔是单笔就超上限；2142~3212 拍 581 笔、3213~4283 拍 465 笔是收款人累计用满。
- 策略源码里没有一处读 `donQuota`、`donCap`、`canReceive`、`donateQuote`（Vc 和 c110 都是 0 处）。
- c110 的局在配额没解除的三个档上调度落地率是 25% / 75% / 68%，c116 三个版本是 0%~1% / 6%~14% / 20%~35%（≥4284 拍 c110 是 91%，c116 是 89%~100%）。原因我没有查清（§4 第 4 条）。一个线索：c110 在解除前发得少得多——2142~3212 拍 24 局一共 55 次，c116 Vb 59 局 6,132 次——而 13 局里这一档没落地的原因主要是累计用满（581 次；仍解释不了 24 次，单笔就超上限 17 次）。

**代码位置。** `Policy.tryDonateToTeammate`：`L4329` 开闸条件和 24 拍冷却；`L4331` 按槽位错峰；`L4500~4506` `pct = min(maxSafePct, idealPct)`，`idealPct` 是 170~260，小于 150 不发；`L4508~4510` `g.donate` 返回真就记冷却、占掉这一拍。

**配额的精确公式**（模拟器 `game.js` `L347~383`；我把线上原文切出来在沙箱里随机比对过 92,218 条捐款指令，不一致 0 条，见 `out/live-donation-check.txt`）：

- 上限 `cap(t)`：开局 15；每逢 `t % 100 == 99` 加一次，`t < 1071` 加 4，`< 2142` 加 6，`< 3213` 加 8，之后加 10。
- 一笔到账 `v` 的捐款记在收款人 `q` 头上的点数：
  `t ≥ 3213`：`cost = 4 + iV(100·v, softCap(q))`，`softCap(q) = min(100×terr[q], 1e9)`；
  `t < 3213`：`cost = 2 + iV(100·v, k(t)·uw)`，`uw = 1 + iV(全图陆地格数, 300)`，`k(t)` = 1、4、10、30、100，分界 357、714、1071、2142；
  `iV(a, b) = floor((a + 0.5) / b)`。
- 受理条件：`used(q) + cost ≤ cap(t)`；`t ≥ 4284` 或收款人是内置 AI 时不限。点数只增不减。
- 税：`iV(64·B, 1024)`，按捐出方的全部余额收，和捐多少无关。到账还受收款人余量限制：`v ≤ 150×terr[q] − bal[q]`。

**方向。**
1. 发之前算这一笔最多能进多少：
   `t ≥ 3213`：`v_max = floor((cap(t) − used(q) − 4) × softCap(q) / 100)`；
   `2142 ≤ t < 3213`：`v_max = (cap(t) − used(q) − 2) × uw`。
   这两个式子是保守取的（`iV` 的取整还能再多放进不到一个点数的量）。再和收款人余量取小。
2. 值不值：税是固定的 `B × 64/1024`，所以到账 `v` 至少要是税的 `λ` 倍才发，即比例 `≥ 64λ/1024`；`v_max` 达不到就不发，把这一拍让给别的指令。
3. `used(q)` 策略读不到，要自己记：自己捐成的（下一个执行拍看到自己的余额少了 `v + 税`、对方多了 `v`）记准确值；别人捐给 `q` 的看不到，保守地按「同队每个编队号都可能在捐」留余量 `μ`，或者走协调器共享（出生协调器已经有这条后端通道）。
4. 一个收款人同一时间只安排一个捐款人（`L4331` 的槽位错峰已经是这个意思，但它不管收款人是谁）。

### 2.8 两处独立的小锁：`isNoFullSend` 要能解；认队友按队伍不按名字

**（a）`isNoFullSend`**

- **证据。** 113 个号里 108 个上过锁；上锁后被守卫拦掉的出兵 914 次（同一笔每 5 拍重下，有重复）。团队局的引擎里没有这条单次出兵限额。
- **代码位置。** `Policy.send` `L3876`：在线时挂一个 `pendingQuotaCheck = {t+1, 发令时余额, 手续费, 想发的兵}`；`Policy.updateShadowQuota` `L3821~3835`：之后 6 拍内看到余额掉得比手续费多，就拿「掉了多少」和「想发多少」比，差得多就置 `isNoFullSend = true`（`L3828`）。全文只有置真的地方（`L3778` 初值、`L3803`、`L3828`、`L3870`），没有复位。守卫在 `L3844~3863`。
- **为什么会误判。** 线上指令一般 7 拍以后才执行，6 拍内看到的余额变化不是这一条造成的：是前一条晚到的小指令、是别的单子先落地、是正在挨打。
- **方向。** 判据换成 §2.1 账本里那一条指令自己的落地记录（在途兵增加了多少），不用余额差；锁要有复位条件（之后任意一条指令足额落地就解）。
- **会在哪里反咬。** A047、A083 我判的是「不明」：这两局锁上以后，守卫拦掉的有一部分正是本来会成摞落地的重复单，锁在无意中起了限流的作用。先解锁、不上 §2.1，这两局的清仓批会变多。

**（b）认队友**

### 2.9 没有排进八项的：手续费

陆攻手续费按余额的 12/1024 收、和出多少兵无关，12 局合计占出征兵的 12.1%；出兵比手续费还少的指令 122 条，白付 178.3 万。我没有把它单列成一项，原因有两个：量级比上面八项小一个档；而且把手续费摊进单价去拦小额指令，在 13 局里已经见过两次反效果——A078 `zero_7` 贴着一块 6 格、0 兵的残地 204 个决策拍不吃（单价 655.8 对 worth 38.5），A073 `alex_k` 岸上的滩头同理。手续费应当作为 §2.1 仲裁器排序时的成本项，不要再做成一道单独的闸门。
