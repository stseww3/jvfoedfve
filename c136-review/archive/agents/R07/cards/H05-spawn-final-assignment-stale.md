# H05 出生阶段结束时，一部分号没有停在协调器最后排给它的点上

- **类型**：观测
- **环节**：出生（协调器 → 宿主 → 服务器）
- **涉及标签**：SP-SWAP-CHURN（7 局 16 例）、SP-OVERLAP（A062）
- **报告位置**：2.1、9.1

## 一句话

协调器在出生阶段反复改指派；最后一条指令没进录像，或者几条在同一步里一起到、先后倒过来，号就停在一个更早的指派上。

## 证据

（`exec_census.txt` A；77 局、686 个号次。）

| 出生阶段结束时 | 号次 |
| :-- | --: |
| 停在最后一次指派上 | 484 |
| 最后一次进了录像，但被同一步里更早的那条盖掉 | 20 |
| 最后一次没进录像，停在更早的指派上 | 132 |
| 一条选点指令都没进录像（见 H04）| 40 |
| 对不上（A005 4 个、A006 6 个）| 10 |

- 至少一个号没停在最后一次指派上的局（不算一条都没进的）：46 局。10 个号全都停在更早指派上的 4 局：A037、A058、A066、A090。
- 同一步里同一个号落了两条以上（指向不同点）的组：录像里的先后和发令的先后相反 945 组、相同 0 组、两种都说得通 211 组。引擎按录像的先后依次生效，所以最后生效的是最早发的那条。
- 我复盘过的局：A062 1 个号、A061 1 个、A091 3 个、A089 4 个没停在最后一次指派上（`cross_match.txt` 表 12）。
- 协调器求解结果变过几次：≥30 次的 40 局、10~29 次的 20 局。

## 不支持 / 要小心

- 停在更早的指派上，不一定比最后一次差；这张卡只说「实际位置和协调器以为的位置不一样」。它对站位（H06）的影响我没有逐局量过。
- 日志只在指派挪动超过 4 像素时记一行，小挪动的指令在日志里没有对应行（`54_spawn_seq.py` 的说明）。

## 机械判据（全量）

`57_exec_census.py` A 节；逐局在 `exec_census.tsv` 的 `endLast` / `endOver` / `endStale` / `endNone` / `grpRev` / `grpFwd` / `grpBoth` 列。

## 怎么证伪 / 还缺什么

- 同一步多条时如果有一组只能按「同序」解释，就说明先后不总是相反（现在 0 组）。
- 先后相反是宿主发的时候就倒了，还是服务器收的时候倒的，要宿主的发送日志才能分。

## 对后面工作的含义（只是分析）

- 模拟器里出生阶段同一步的多条指令要按「后发的先生效、先发的最后生效」重放。
- 评估站位时，协调器的最终方案和实际落点要分开看。
