# H12 捐款：4284 拍前发出的八成半没成交（主要是引擎的受捐额度）；成交的每送到 100 兵另付 38 兵的税

- 现象的证据等级：**E2**（日志口径 123 局 22872 条捐款日志行；录像口径 1500~3000 拍 7582 行里落地 428 条）
- 「值多少地」的证据等级：**E1**（税和被拒是硬账；「这些兵如果不这么捐能换多少地」没有量过）
- 对应模式：NEW-DN-01（快出局的号没人救）、NEW-DN-02（小比例捐款税比到账多）、NEW-DN-07（两个号来回捐）、NEW-DN-12（往快满的队友身上捐）、NEW-DN-17（救援刚到就被捐回去）；
  单局里还有 NEW-DN-04 / 05（捐给停摆的空壳、捐给名字撞池子的陌生人）、NEW-DN-08 / 13（单笔超额、被拒后原样重发）、NEW-DN-10（卡顿时连发、追平时一起扣）

## 一句话

捐款函数只看「我有没有富余、对方缺不缺」，不看引擎让不让收。4284 拍以前引擎对每个受捐方有累计额度，日志里那段的捐款行，看得到结果的里面 85% 是被拒的；
冷却一过原样重发。成交的那些，手续费是捐出方**全部余额**的 6.25%，和捐多少无关——比例小的、对方快满的、两个号来回倒的，税比到账还多。

## 可证伪的陈述

1. t<4284 的捐款日志行，看得到成交的不到两成；t≥4284 的八成成交。
2. 成交的捐款，手续费合计是到账的三到四成；squad8（比例固定 51/1024）手续费比到账还多。
3. 有录像的局里，1500~3000 拍日志写了捐款、录像里真的落地的不到一成。
4. 快出局的号大多一笔成交的捐款都没收到。

## 机制

### 引擎（`game.js`）

- `donate` L404-416：想捐 `(pct+1)/1024 × 余额`，先按 `receiverRoom`（L340-345：对方余额不超过 150×领土）夹小；再 `bookDonation`（L370-376）查受捐方的累计点数，超了整单不成交（不收税）；
  然后 `transfer`（L388-401）：手续费 = `⌊64×余额/1024⌋`，按捐出方的全部余额收，和 pct 无关。
- 额度（`donationCost` L348-357、`donCap` L124 起始 15、`donationCapTick` L379-383 每 100 拍 +4 / +6 / +8 / +10）：
  t<2142 一笔到账 v 耗 `2 + ⌊100v ÷ (30×uw)⌋` 点（`uw = 1 + ⌊全图陆地/300⌋`），2142~3213 分母是 `100×uw`，t≥3213 是 `4 + ⌊100v ÷ (100×受捐方领土)⌋`；
  全场共用一个上限，t=1499 是 85 点、t=2141 是 121 点、t=3212 是 209 点、t=4199 是 309 点（`src/engine/live-donation-check.txt` B2，和线上原文比对 0 条不一致）。
  `donationFree` L360-362：t≥4284 或受捐方是空壳 / 内置 AI 时不查。
- 换成兵：42 万格的图上，t<2142 一个受捐方**开局以来累计**最多收 5 万兵上下，t<3213 累计 29 万上下（同一文件 B3）；t≥3213 每收到「1 倍自己领土」的兵耗 1 点。
  所以 4284 拍前想把兵集中到一个号身上，引擎不让；4284 拍后随便。

### 策略

- 五个策略文件里 `donateQuote` / `canReceive` / `donQuota` / `donCap` / `receiverRoom` 一次都没出现。
- c110 `tryDonateToTeammate` L4369-4499：L4372 只看 18 拍冷却；救援分支 L4423-4445 pct = `min(maxSafePct, 155 或 240)`；盈余分支 L4462-4490 pct = 被围 ? (密度>110 ? 280 : 185) : 153。
  候选只挑同队的 Boss 或名字池里的名字（L4424 / L4467 `isOurSquadBot`），不看 `g.isBot`（对方是不是已经停摆）、不看对方还装得下多少、不看对方刚才是不是捐过来。
- c116 `tryDonateToTeammate` L4325-4518：L4329 要 t≥1500、自己 ≥1200 格、≥35000 兵、24 拍冷却；按 `defense_dispatch` / `offense_dispatch` / `yield_opt_dispatch` 三种理由挑人，
  pct 不到 150 不发（L4506；c116-va 是 128，c116-vb 是 180）。同样不查额度。
- g09：比例固定 51/1024（L4455、L4824、L4853、L4904，注释 "Strictly 5%"）。到账 5.08% 的余额，税 6.25%——每一笔都是税比到账多。
- 日志行是在 `g.donate(...)` 返回真之后写的（c116 L4508-4514）；线上这个返回值只表示「指令发出去了」，所以被拒的也写了日志、也记了冷却。
- 捐款只在这一拍没有别的指令时才试（c110 L4922、c116 L4962 `if (this.cmds === cmdsBefore)`），所以被拒的捐款不占进攻指令的位置；它的代价是「该挪的兵没挪成」，以及卡顿时的连发（下面）。

## 和结果的关系（`xsig.txt` [XG-C]）

- NEW-DN-01：赢的局 8/16（50%），没赢的局 91/107（85%），Fisher p=0.0031（没过 Bonferroni 门槛）。
- NEW-DN-07（来回捐）在赢的局里反而多（62% 对 50%）——赢的局打得久，4284 拍以后捐款放开，来回的机会多。它是「后期才有的浪费」，不是输的原因。
- 没有做「捐款成交率 × 结果」的相关：成交率主要由局打到多晚决定。

## 反证和混杂

- 被拒不收税。4284 拍前的 14847 行被拒本身没有直接损失；损失是间接的：该到前线的兵没到（NEW-DN-01），以及富的号顶着软上限 / 硬上限停着（H08）。间接损失没有量。
- 「成交」的判定靠余额观测，有 1191 行定不了（5%）；录像口径只有有录像的局。两种口径量级一致。
- 手续费 ÷ 到账 38% 是「成交的那些」的平均，按发令时余额估；捐出方被围、自己的地不产息时（余额早已超过软上限），留着也是负利息，捐出去付 6.25% 不一定亏。检测器不区分这种情况。
- 野人同样受额度墙限制，他们的捐法和编队号不一样（`xdon.txt`，107 份录像里发到服务器的捐款指令）：
  - 野人 3595 条，其中 17% 是「几乎全捐」（pct ≥ 900）、30% 在 63~127；机器号 6580 条，pct ≥ 512 的只有 3 条（[XO-B]）。
  - 野人的全捐 626 条，出现在 76 份录像里；发令拍的中位 4634（四分位 3549~5549）；24% 捐完 300 拍内这个席位就有「离开」指令，37% 捐完以后这个席位再没有任何指令——多数是临走 / 临死前把兵留给队友（[XO-F]）。
  - 「很多人喂一个号」（同一个受捐席位 300 拍内收到 ≥3 个不同席位、合计 ≥5 条）：受捐方是野人的 22 个窗、11 局，起点 1 个在 3213 拍前、8 个在 3213~4284、13 个在 4284 拍后；
    受捐方是机器号的 191 个窗、54 局（[XO-D]）。按这个口径，集中喂一个号是编队号自己做得多，野人做得少而且晚。
  - 一局里野人的捐款指令，收得最多的那个席位占 32%（中位；给它捐过的席位数中位 2 个）（[XO-C]）。
